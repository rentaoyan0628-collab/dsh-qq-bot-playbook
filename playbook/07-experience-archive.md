## 痛点

三个东西都叫「记忆」，但都解决不了这件事：

| 已有的东西 | 它记的是什么 | 缺的是什么 |
|---|---|---|
| DSH 会话上下文 | 这一次对话的最近若干条 | 会话一换、一重启，全没了 |
| 会话摘要（400 字） | 这次聊了什么 | 具体哪句话、谁说的、什么时候 |
| 记忆插件（会淡忘的长期记忆） | **你告诉它的事实**（住哪、养什么） | **发生过的事**（那天聊到几点、答应了什么） |
| 桥接的 recentMessages | 每个会话最近 100 条 | 跨会话、跨平台，而且隔久了就滚掉了 |

于是会出现这种对话：

> 群友：「你上次不是说要去看那个展吗」
> 它：「啊？哪个展」

它没有撒谎，也不是不肯记——**它手边真的没有那条**。而你能做的补救，通常是把聊天记录翻出来粘给它，一次几十条，烧掉半屏上下文，然后下次还得再粘一遍。

经历库就是为这个缺口做的：**把「谁在什么时候说了什么」落成本地原文，把「发生过什么」单独归纳一层，再给它几个查/读/记/改的工具。**

## 设计

### 一句话

一个**独立的本地 SQLite 库**，两层数据（原文 + 经历），七个工具，一个常驻采集进程。不改桥接、不改任何插件。

```
QQ 群/私聊 ─┐
B站直播弹幕 ─┤→ 采集器（每 60 秒，增量、幂等）→ archive.db ─→ MCP 七个工具 ─→ 大肥鱼
抖音私信   ─┤                                    ├─ 原文层（谁/何时/说了什么）
鱼的心情   ─┘                                    └─ 经历层（发生了什么/偏好/约定/感受）
```

### 两种出口（这是唯一的安全设计）

我试过按「权限分级」设计：自己人一层、群友一层、陌生人一层，每层能看不同的东西。**放弃了**——层级一多，判断就变成猜，而且每次查询都要多问一句「你确定吗」，最后人会学会无脑点同意。

最后只留两个出口：

| 出口 | 内容 | 谁能看到 |
|---|---|---|
| **经历摘要** | 归纳过的事实：聊过什么、什么约定、什么情绪、关系怎么变的 | 任何一个问起的人（在群里问就在群里答） |
| **本人原文** | 这个人自己说过的原话，带时间和平台 | **只给这个人本人** |

规则也很短：

- 本人问自己的事 → 可以读原文，可以在当前会话（哪怕是在群里）照实回答；
- 别人问起 → **只用摘要**，不复述原文；
- 问「我们是不是聊过 X」 → 先按人/时间/事件搜，找到就给相关经历，必要时附上他自己的原文；
- **搜不到就说搜不到**，不许根据印象编一条。

「问的人是谁」由模型按**入站消息**判断（私聊的会话 key 里就带着 QQ 号，群聊里带着发言人），**没有第三层权限、没有额外确认弹窗**。

代价我认了：判断错了会漏。所以人格里写死一句——**拿不准就用摘要，别复述原文**。宁可少说一句，不要张冠李戴。

### 采集：只记真的发生过

| 来源 | 从哪读 | 纪律 |
|---|---|---|
| QQ 群/私聊 | 桥接的 state/social-v2.json | 每个会话只缓冲 100 条，所以必须定时增量 |
| B站直播弹幕 | 刷 B 站插件的 logs/danmaku.jsonl | **只认 result: sent** |
| 抖音私信 | 刷抖音插件的 memory/dm-*.json | 双方都记，带 direction |
| 鱼的心情 | 心情插件的 state.json | 只取按人分槽的那几条 |
| B站私信 | — | **没接**：插件读完就丢在内存里，要挂钩子才拿得到 |

三条硬规矩：

1. **只读别人的文件，只写自己的库。** 采集器挂了，QQ、B站、抖音照常跑，只是不继续记新消息。
2. **幂等。** 同一条消息抓十次也只有一条（按平台 + 会话 + 消息 id 去重）。否则一次重启就把库撑成十年前的样子。
3. **不假装全量。** 没接的源就写「没接」，README 里明说。

### 为什么不做成插件

这是整件事最重要的一个决定。

```
❌ 改桥接：在 social-v2 落盘的地方顺手写库
   → 桥接一改，QQ 就不回消息了；想摘掉经历库，得改回桥接

✅ 独立进程：读桥接已经写好的文件，写自己的库
   → 经历库坏了自己死；qq-bridge 的 update 不受影响；摘掉 = 关进程 + 卸 MCP
```

DSH 这边的接入只是**注册一个 MCP**（stdio，零依赖手写 JSON-RPC），人格里加一段「什么时候查、什么时候记」。两者都能一条命令卸掉。

### 跨平台身份：一个人不止一个 id

同一个人在 QQ、B站、抖音是三个号。库里有张 people.json 身份表，把 id 挂在一个人名下：

```json
{ "merges": [ { "name": "某个人",
  "ids": [ {"scope":"qq","id":"100000001"},
           {"scope":"bili_uid","id":"8126336"},
           {"scope":"bili_room","id":"5370564"} ] } ] }
```

改完跑一次 ingest 生效。建错了人，用维护脚本按「把 A 并进 B」合并，消息和身份一起搬——**搬之前先备份**。

### 七个工具

| 工具 | 干什么 |
|---|---|
| archive_search | 找经历 + 原话，可按人/时间/关键词 |
| archive_read_own | 读某个人和鱼的原文（只给本人） |
| archive_timeline | 按时间看最近发生什么，跨平台 |
| archive_remember | 写一条经历（谁/何时/发生了什么/偏好/约定/感受/关系变化） |
| archive_correct | 改一条经历，旧值留在 correction 表 |
| archive_status | 体检：多少条、各平台水位、哪里断了 |
| archive_people | 库里都有谁 |

标签 stated_fact / model_judgement / feiyu_mood **只是内容标注，不是权限层**——它们的作用是防止「把自己的猜测当成对方说过的话」。

## 坑

1. **缓冲只有 100 条，这是硬约束。** 桥接每个会话只留最近 100 条，隔两天不抓，中间那段就永远补不回来了。所以采集器必须常驻（60 秒一轮）、必须单实例（pid 锁），否则两个进程抢着写。

2. **「发出去」和「我以为发出去了」不是一回事。** 弹幕日志里同时有 draft / throttled / rejected / failed / sent，**只有 sent 算说过**。如果按「调了工具」记，它就会替你记下一堆从没发出去的话——这种错误在事后核对时最伤。

3. **原文在涨、经历层不涨，是最贵的坑。** 真实数字：跑了不到两天，原文 1477 条（对方 855 / 我说 622），57 个人，**经历摘要只有 2 条**。
   症状不是报错，是「它记得住原话，说不出故事」——你问它「我们上次聊的那家店」，它能把十条原话贴给你，但说不出「你们聊到想去、但还没去」。
   **根因：工具做了，不等于它会用。** 工具的 description 只说明「能写」，模型不会自己意识到「这一段值得记一条」。
   修法只有一条：**在人格里写清楚什么时候该记**（有人给出新的事实/约定/情绪转折、关系变化、值得回味的玩笑），并明确「别把每句话都记成经历」。

4. **检索结果不能整段倒进上下文。** 一次翻出 300 条，等于把历史和 token 一起烧了，还会把无关的人扯进来。默认取几条、按相关度排，只给「够回答问题」的量。

5. **同一人三个 id，合并前必须备份。** 合并是不可逆的搬数据操作；备份脚本要能一条命令 restore，且 restore 之前先自动再备份一次。

6. **模型判断要留痕。** 「鱼觉得这个人今天心情不好」和「这个人说他不开心」是两件事。前者标 model_judgement + 置信度 + 原因 + 关联对话，后者标 stated_fact。混在一起，过一周连它自己都分不清哪句是真事。

7. **没接的源要写出来。** B站私信到现在还是空的——插件把消息读进内存就用掉了，不留文件。这种「看起来应该有、其实是空」的缺口，比报错更容易骗人。

## 验证

不用问模型，命令行就能验：

```bash
node cli.mjs status                    # 多少条、各平台水位、最近一次采集
node cli.mjs search 关东煮              # 全文找一件事
node cli.mjs read 年银滔 --limit 20     # 看跟某个人的原文
node rollback.mjs list                 # 备份列表
```

模型侧调 archive_status，应该看到：

- 每个源都有**最新时间**（不是只有条数）；
- 原文条数在涨；
- 经历条数也在涨——**如果只有第一个在涨，就是坑 3**。

## 可以直接发给 AI 的需求

> 我要给 QQ 机器人做一个本地经历库，让它记得住人、也说得清事。请在我这台机器上：
> 1. 建一个**独立目录** + SQLite（开 WAL），分两层：原文（平台/人/会话/时间/消息 id/方向/正文）和经历（谁/何时/发生了什么/偏好/约定/感受/关系变化，每条指回原文）
> 2. 采集这几个源（按我机器上实际有的挑）：QQ 群聊私聊、B站直播弹幕（**只认真的发成功的**）、抖音私信、心情插件的按人分槽记录。要求：幂等、只读别人的文件、只写自己的库
> 3. 写一个常驻采集进程：60 秒一轮、隐藏窗口、pid 单实例锁、可 --stop；它挂了不能影响 QQ/B站/抖音
> 4. 用 MCP（stdio）暴露七个工具：搜经历、读本人原文、看时间线、写经历、改经历（旧值留痕）、体检、看人
> 5. 两种出口：**归纳摘要可以对外说；本人原文只给本人**。判断「问的是谁」按入站消息来，不要加第三层权限、不要每次弹确认；人格里写死「拿不准就说摘要、搜不到就说搜不到、不许编」
> 6. 一张跨平台身份表（QQ / B站 uid / B站房间 / 抖音），支持把同一个人合并，合并前自动备份
> 7. 备份/还原脚本，加自测：增量不重复、不改源文件、能写能改能纠正
> 8. 人格里写清「什么时候该记一条经历」——这条比前面七条都重要，不然库会变成聊天记录废墟
> 做完给我 status 的输出，让我看看各平台水位和经历条数是不是都在涨。
