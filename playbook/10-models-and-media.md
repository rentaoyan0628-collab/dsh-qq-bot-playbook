## 一、模型：预设 + 按会话分流

### 痛点

桥接这一类东西通常只认一个全局模型配置，于是会遇到两件麻烦事：

1. **换模型要改配置文件重启**，而且改错档位（思考强度）会直接报错，报错还很难懂。
2. **一群一私聊不能分开**：群里想用便宜快的，私聊想用稳的，共用一个全局值就只能二选一。

### 设计：把「模型」变成一个可命名的预设

一个预设 = 名字 + 提供方 + 模型 + 思考强度。配置里存一份预设表，再存一个「当前用哪个」的指针：

```text
profiles:
  gpt:      { provider, model, reasoningEffort }
  deepseek: { provider, model, reasoningEffort }
  gemini:   { provider, model, reasoningEffort }
activeProfile: deepseek
```

要点：

- **切换要在线、不重启**：改完下一个会话立即生效，已经开着的会话用「会话级设置模型」补一刀。
- **控件从真实目录生成**：提供方和模型列表不要去网上抄，向宿主问一遍目录（有哪些提供方、每个模型支持哪几档思考强度）。
- **写之前先校验**：档位不在该模型的列表里就拒绝，并说清楚可选值。

真实的报错长这样，说明校验真的在工作：

```text
模型「x」只支持思考强度 off / low / high / max（收到 medium）
provider「y」下没有模型「z」（可选：…）
```

### 按会话分流

配置里再加一张小表：群聊用哪个预设、私聊用哪个预设。每条消息进来时按会话 key 取预设，再决定这次要设成什么模型。

注意三点：

- **「已设置」要以签名为准**，不要按会话 id 记一个布尔值。签名 = 模型选择代数 + 提供方/模型/档位；配置一变代数就变，所有会话自动失效重设。
- **控制台上的一键切换只管全局**。全局切了、分流还指着旧预设时，群里照样走旧模型 —— 这是最容易「以为切了其实没切」的地方。
- **订阅制要单独处理额度**。按订阅计费的通道，token 单价那套预算闸对它没有意义；要么跳过预算判断，要么给它单独设一条上限，不要两头都不管。

### 换模型会丢什么

只丢「这个会话的对话历史」，不丢记忆（见 [09](09-memory-sharing.md)）。另外两个真实差异值得提前知道：

| 差异 | 表现 | 应对 |
|---|---|---|
| 看图能力 | 有的通道会直接丢图片，模型回「我看不到这张图」 | 换模型后先用一张图试一次，别等群里发图才发现 |
| 档位命名 | 有的模型没有「off」，有的默认档不一样 | 一切以宿主目录为准，不要硬编码 |
| 大会话 | 上下文堆到几十轮之后，某一路通道可能整轮零输出 | 老会话先摘要再开新会话，不要在巨型会话上硬扛 |

## 二、发图：超时不等于失败

### 痛点

最典型的事故：**图片已经到对方手里了，发送方这边报超时**，然后模型判断「失败了」，重发一遍 —— 群里出现两张一样的图，或者一次小事变成两次刷屏。

根因不在模型：出图/上传是两段耗时，客户端等回执的截止时间（常见 30 秒）比网关上传播完成的时间短。**读超时只说明「没等到回执」，不说明「没送到」。**

### 设计：三种结果，不是两种

发送结果必须分三种，而不是成功/失败：

| 结果 | 含义 | 模型该做什么 |
|---|---|---|
| 成功 | 拿到消息 id | 正常说一句 |
| 失败 | 明确被拒（参数、权限、离线） | 可以照实说失败，必要时改一次参数 |
| **未知** | 请求已提交、回执没回来 | **不许重发、不许断言失败**，只说「发出去了但没确认」 |

落地要做三件事：

1. 把超时门槛放宽（几十秒 → 两分钟级），别再拿 30 秒卡图片。
2. 超时/网络中断时给错误打一个「投递未知」的标，别当成普通异常往上抛。
3. 工具层把这个标翻成一句人话：「可能已经发出，不要重发」。

### 图片库：先列再发

如果它经常「明明有图还现画」，通常不是想象力过剩，是**它不知道图在哪**。做法是给一个共享图片库（一个目录 + 一组工具）：

- 存：收到群图时可以存（要人工触发，不要全自动收），出图后自动落一份；
- 列：给编号和元信息；
- 读：按编号看图；
- 发：按编号发到当前会话。

配套一条纪律：**先列再发**。模型手里没有编号时，第一步永远是「库里有啥」，不是「我画一张」。

## 三、发文件：路径不是通行证

### 痛点

图片走的是「图片消息」，文档、压缩包、音频走的是另一条通道（群文件 / 私聊文件）。两条通道不通用，所以经常出现「图能发、pdf 发不出去」。

### 设计：一个可发送目录 + 四条硬规矩

| 规矩 | 为什么 |
|---|---|
| **只允许白名单目录** | 否则等于把整台机器变成「任意文件发送器」 |
| **路径必须解成真实路径再比对** | 软链接、`..`、盘符大小写都能绕过字符串比较 |
| **有大小上限** | 网关和 QQ 都会在某个体积上直接失败，晚失败不如早拒绝 |
| **文件名要清洗** | `/ : * ? " < > |` 和控制字符会在某些系统上炸掉上传 |

另外：解析不到文件时，报错里**只回「可发送目录是哪几个」**，不要回目录里的完整列表 —— 列表泄露等于把家里抽屉报给对方。

## 四、频率：三个闸，别只做一个

| 闸 | 管什么 | 建议初值 |
|---|---|---|
| 发送限流 | 每分钟 / 每小时最多几条 | 分钟级个位数、小时级几十条 |
| 唤醒概率 | 群里没人叫它时，多大概率自己醒 | 冷群 1%～5%，热群按体感调 |
| 运营方硬锁 | 某些群只允许被 @ | 写进配置，模型改不动（见 [08](08-operations-layer.md)） |

调参经验：**先把广度压下来，再调深度**。也就是先降概率（少冒泡），再调限流（别刷屏）。反过来调会出现「平时不说话，一说话连发五条」。

## 五、看直播这类能力，为什么应该是独立插件

如果你要给 bot 加「去 B 站直播间听弹幕 / 发弹幕 / 自动陪聊」这类能力，建议**单独开一个仓库**，不要塞进 QQ 桥接的 playbook 里。三个理由：

1. **依赖不同**：它要的是 B 站账号与房间授权，跟 QQ 一点关系都没有；不装 QQ 的人也应该能用。
2. **风险不同**：往别人房间里说话，是「对外发声」，需要自己的放行名单和发送闸，不该借用 QQ 的白名单。
3. **演化速度不同**：直播接口变得比 QQ 快，独立仓库可以自己发版，不用跟着桥接走。

参考实现：[rentaoyan0628-collab/dsh-bili-live](https://github.com/rentaoyan0628-collab/dsh-bili-live)（本仓库作者自己写的独立 DSH 插件：只读弹幕、挂机、可选自动陪聊；进房与发弹幕默认都关着，要人放行）。

边界提醒：这类能力**不要**顺手接进 QQ 会话当作聊天素材，除非你真的想清楚了两件事 —— 转写内容会被发给模型提供方，以及「听到的」不等于「看到的」。

## 坑（都是真踩过的）

1. **「切了模型但没生效」**：控制台切的是全局预设，分流表还指着旧预设。切完要回读接口确认「群 / 私聊各自的最终值」。
2. **图片超时被当失败**：对方已经收到，模型又说「发送失败，我再发一次」。看到「投递未知」就当已发出处理。
3. **文件发送没有回执语义**：上传接口返回的是文件 id，不等于对方下完了；别承诺「已送达」。
4. **文件名带中文/空格**：命令行拼参数时会被拆开，能走 API 就别拼命令行。
5. **限流调太狠**：分钟级降到 1 条，长回复会被截成一条，反而更像机器人。
