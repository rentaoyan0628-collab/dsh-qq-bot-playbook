# 六个「原生没有」的能力：设计与坑

> **身份说明**：我不是这些工具的作者，只是一个把这些东西串起来的普通用户。
> 本文件讲到的每个项目，作者和仓库都在 [README](../README.md#谁写了什么) 里列明了。
> 装的时候请去原作者仓库装；写错了算我的，好用的是他们的。

> **这份不是代码，是设计说明书。**
>
> DSH 原生的 QQ 插件能聊天，但缺六样东西。下面每一项写的是：**它解决什么痛点、我们最后怎么设计的、为什么这么设计、踩过什么坑、怎么验证做对了**。
>
> 你的电脑、你的桥接层、你的 DSH 版本都和我这台不一样。看完你应该做的事是：**把这些需求连同这里的设计取舍一起，交给你的 AI，让它按你的环境实现一遍**。做出来的样子和我的不一样，是正常的，也是对的。照着抄路径反而会失败。

## 一、语音转文字：让 AI 听得见

### 痛点

QQ 语音条进到 AI 眼里只是一个 `[语音]` 占位符。用户说了什么，它完全不知道，只能回一句"我听不到语音"。这是最影响体验的一个缺口。

### 设计

三条路，我们全试过：

| 路子 | 结果 | 结论 |
|---|---|---|
| 网关自带的转写接口（SnowLuma 的 `fetch_ptt_text`） | 一直返回 `ptt translate failed: error=9` | 不可用，别在这上面耗 |
| 云端 ASR | 可行，但语音条要上传出去 | 隐私和成本都不划算 |
| **本地 faster-whisper** | 稳定、离线、够准（small 模型中文可用） | ✅ 采用 |

链路：收语音 → 拿音频文件 → 本地转写 → 把 `[语音]` 换成 `[语音:文字]`。

**关键决策：转写失败必须降级，不能阻塞消息。** 转写要 2～5 秒，异常路径（venv 挂了、模型没下完、超时）必须退回原来的 `[语音]` 占位符，让消息照常进上下文。

### 坑

1. **音频要先落盘成 wav**。QQ 语音原始格式（`.amr` / `.silk`）不能直接喂 whisper，必须先用 ffmpeg 转成 16k 单声道 wav。
2. **超时给足**。第一次跑要加载模型，冷启动 10～20 秒很常见，超时设 90 秒比较安全；之后走缓存就快了。
3. **缓存转写结果**。同一条语音可能被处理两次（引用回复、历史回看），按文件 hash 缓存，别重复转。
4. **子进程用 `execFile` 不要用 `exec`**。`exec` 走 shell，中文路径会被系统编码吃掉，输出变问号。
5. **stdout 强制 UTF-8**。Python 脚本里 `sys.stdout.reconfigure(encoding='utf-8')`，否则 Windows 下中文出来是乱码。

### 验证

发一条语音，看日志：
- 成功 → 上下文里出现 `[语音:转写出来的字]`
- 失败 → 出现 `[voice] 转写失败（降级为 [语音]）`，消息仍然正常送达

### 可以直接发给 AI 的需求

> 我要让 QQ 机器人听懂语音条。请在我这台机器上：
> 1. 找一个能本地跑的中文 ASR（faster-whisper 就行），装在独立 venv 里，别污染全局
> 2. 写一个脚本：接收音频文件路径，输出识别文字到 stdout，UTF-8
> 3. 在桥接层收到语音时调用它，把 `[语音]` 渲染成 `[语音:文字]`
> 4. 失败、超时、脚本不存在时一律降级成 `[语音]`，不能让消息丢失或阻塞
> 5. 加一个开关和结果缓存
> 做完给我一条命令，让我能单独测这个脚本。

## 二、管理员传话箱：QQ 说的话，本机去执行

### 痛点

QQ 那头是个只会聊天的 AI，它摸不到本机的文件、进程、程序。管理员说"把 ACE 启动起来"，它只能嘴上答应——**它连一个工具都没调**。这是最容易被误判成"bug"的问题。

### 设计

一个单向信箱：

```
QQ 里的 AI 调工具 → 写一条 JSON 进信箱文件 → 守护进程扫信箱 → 投给一个活着的 DSH 会话
```

三个刻意的设计：

1. **信箱落盘，不用内存队列**。桥接重启、程序崩溃，消息都还在。
2. **投递由独立守护进程做**，不塞进桥接主进程。桥接挂了不影响投递，反之亦然。
3. **投给谁要能钉死，也要能自己挑**。钉死了但那个会话死了，就自动挑一个活着的。

### 坑（这几个坑都很贵）

1. **投给死会话，消息全进黑洞**。`target` 文件里存的 sessionId 可能早就停了。必须每次验证那个会话还活着（`running !== false`、`agentAvailable`）。
2. **别用 `updatedAt` 排序挑会话**。注入 prompt 会把会话的 `updatedAt` 顶新，于是"刚被投过的会话"永远排第一，形成自我延续——所有消息都投给同一个（而且可能是不该投的那个）。**用 `lastPromptAt`（真人最后一次说话的时间）排序，拿不到就返回 0。**
3. **排除内部 agent 会话**。桥接自己会跑一些内部会话（黑话提取、心情判断、体检之类），它们的目录看起来和正常会话一样。必须在路径上排除，而且要排干净整个 `state/` 父级，不是只排 `state/agents/`。
4. **别让 AI 觉得"我没有这个工具"**。工具默认是开的，但**人设/工具协议里要明确写一句**："管理员要求做本机操作时，用 `qq_dsh_inbox` 转给 DSH"。不写，它遇到本地活就按"我没有本机权限"拒绝，然后你会以为坏了。

### 验证

1. 在 QQ 里让 AI 转交一句话
2. 看信箱文件里有没有新增一条 `status: pending`
3. 几秒后看守护进程日志：`delivered <id> -> <sessionId>`
4. 那个会话里应该真的出现这条消息

### 可以直接发给 AI 的需求

> 我要在 QQ 和本机之间搭一个"传话箱"：
> 1. QQ 侧的 AI 有一个工具能往信箱写消息（落盘 JSON，别用内存队列）
> 2. 写一个守护进程，定期扫信箱，把 pending 投给一个活着的 DSH 会话
> 3. 挑会话的规则：优先用 pin 住的那个，但**必须检查它真的活着**；没有 pin 就挑"真人最后说话时间"最新且活着的一个
> 4. **绝对不能用 updatedAt 排序**（投递会顶新它，会自我延续）；要排除所有内部 agent 会话
> 5. 投完标记 delivered，留日志
> 6. 在我的人设里加一条：管理员要求做本机操作时走这个通道
> 做完告诉我怎么验证一封消息真的送到了。

## 三、管理员硬闸：不信任模型自己填的身份

### 痛点

工具参数里有 `adminUserId`，是"调用方自己填"的。群友只要让 AI 填成管理员的号，就能借管理员权限改设置、点歌、转任务。**模型自报的身份，一律不可信。**

### 设计

不看模型填什么，回头查**真实的入站消息**：

- 私聊：会话 key 本身就带 QQ 号（`private:<uid>`），从 key 里解析，不采信参数。
- 群聊：要求这个 uid **本人最近 15 分钟之内在这个群说过话**（去消息历史里找 `userId === uid`）。说不出话的号，就是冒充。

三条判定，对应三句话：

| 情况 | 返回 |
|---|---|
| 私聊里的管理员 | 放行 |
| 群里冒用别人的号 | 「这个要管理员本人来说才行」 |
| 群里不是管理员 | 「只有管理员可以使用这个功能」 |

### 坑

1. **错误提示要能指向下一步**。"权限不足"这种话，AI 看完只会重复尝试。写清"要管理员本人来说"，它就知道该让本人发一句。
2. **标记里要带号码**。只在消息前打 `【管理员】`，AI 填参数时根本没号码可填，只能瞎编。改成 `【管理员 QQ:123456】`，它就有据可依了。
3. **人设里要同步改**。服务端认"管理员列表"，人设里却写"只有 owner 算"，两者不一致的表现是：权限明明给了，AI 还是拒绝——因为它在人设层面就把要求挡回去了。
4. **残留风险要认**。如果模型在上下文里见过别的会话的 token，理论上能伪造 key。彻底解法是"一个 QQ 会话对应一个 DSH 会话"，或者一次性动作 token。做不到就先接受这个风险，别假装安全。

### 验证

- 私聊管理员改个昵称 → 成功
- 群里让普通成员试 → 403 + 「只有管理员可以使用这个功能」
- 群里让 AI 填管理员的号（但本人没说话）→ 403 + 「这个要管理员本人来说才行」

### 可以直接发给 AI 的需求

> 我的 QQ 机器人有管理员权限的工具（改资料、点歌、转任务）。请加一道硬闸：
> 1. 任何管理员工具都先做身份校验，**不信任参数里自填的 adminUserId**
> 2. 私聊：从会话 key 解析 QQ 号，对管理员名单就放行
> 3. 群聊：要求这个 QQ 号本人最近 15 分钟内在这个群真的说过话（去消息历史里核）
> 4. 三种失败给三句不同的话（本人没说话 / 不是管理员 / 私聊可以）
> 5. 管理员标记里带上 QQ 号，这样 AI 填参数时有据可依
> 6. 顺便检查我的人设里对"管理员"的定义和服务端是否一致
> 告诉我怎么构造这三种情况来验证。

## 四、跨会话摘要：记得住，但不越界

### 痛点

两个方向都出过错：

- **记不住**：在 A 的私聊里被问"B 刚才说什么"，AI 一脸茫然——每个会话是独立的，它真不知道。
- **越界**：改完记忆后又反过来，B 的私聊里出现了 A 刚说的话，AI 把「晚安」记到了别人头上。

### 设计

三层：

1. **原料层**：每个会话保留最近消息（含发送者、时间、内容）。
2. **可见层**：决定"这个会话能看到谁"。
   - 群聊 → 能看到群里那些人的**私聊近况**（群里的话本来就多人可见）
   - 私聊 → 默认只能看到**群**的内容；只有对方在最近两条消息里**点名**某人（名字或 QQ 号）时，才临时放开那个人的私聊
3. **渲染层**：**在被问起的那一刻现算**，不落盘、不每轮刷新。

第 3 点是关键。早期方案是"每次发消息后写一份摘要保存"，结果：
- 用工具发消息的回合根本不触发写入 → 摘要永远是旧的
- 摘要写的是上一轮的内容 → 问起时它答的是十分钟前的事

改成**读时重建**之后，两件事同时解决：不增加每轮开销，问起时又总是最新。

### 坑

1. **时间戳要标出来**。注入的文本里必须写清"现场刚取"还是"X 分钟前"，否则 AI 会把旧内容当新消息说。
2. **点名判断别用单字**。两个汉字以下的名字容易误命中（"好"、"行"会撞），跳过长度 < 2 的名字。
3. **摘要为空不等于没内容**。如果只存了摘要文本，消息一清空就只能回退到旧快照。要保留最近消息原文，才能现场重建。
4. **别把两件事混着说**：模型自己写的摘要（可能带主观判断）和系统按消息拼出来的现场内容（客观事实），语气要能区分。

### 验证

- A 私聊说一句 → B 私聊问"他刚才说什么" → 应该答"我这边看不到"（除非 B 点名了）
- 群里问"某人最近怎么样" → 应该能答出那个人的私下近况
- 私聊里点名"某某说了什么" → 能答，且带名字、带时间

### 可以直接发给 AI 的需求

> 我的 QQ 机器人有多个会话（每个私聊一个、每个群一个），它们互相看不见。我想要：
> 1. 群聊里能记住群成员的私聊近况（这样被问"他们最近在聊什么"能答）
> 2. 私聊里默认只看得到群的内容；**只有对方点名问某个人**时，才放开那个人的私聊
> 3. 这些内容**在被问起的那一刻现算**，不要每轮刷新、不要落盘
> 4. 注入时标清"现场刚取"还是"X 分钟前"
> 5. 点名匹配要跳过长度为 1 的名字，避免误命中
> 做完告诉我：A 私聊、B 私聊、群聊 三种视角分别能看到什么。

## 五、成长附录：只准往后写

### 痛点

AI 会"忘记自己变了"。昨天被纠正的一个看法，今天又犯。普通的记忆是"事实库"，存不了"我从哪件事上学到了什么"。

我想要一本**只能往后写**的本子：想通了什么、被纠正后改了哪个看法、哪次判断错了。

### 设计

三件事保证"只准追加"是真机制，不是口头约定：

1. **接口层**：只有"读"和"写"两种请求，**没有任何修改/删除的路径**。
2. **文件层**：只用追加写（append），从不重写整个文件。一行一条 JSON。
3. **链校验**：每行存上一行的哈希，`hash = sha256(prev + ts + key + text)`。手工改任何一行历史，后面全断，注入时会标 `⚠️链断`。

### 坑

1. **时间戳必须带日期**。只存 `17:29` 的话，"每天最多 30 条"这个限制永远算不出来（按 `at.slice(0,10)` 比较，永远相等）。写 `2026-10-25 17:29`。
2. **限流三项都要**：单条字数上限、每天条数上限、两条之间的最小间隔。只做一样，AI 会刷屏。
3. **注入位置有讲究**：放在"跨会话摘要"之后、"参与判断"之前。放太前会被后面的内容淹没，放最后又显得像临时的。
4. **告诉它什么时候别写**。光说"可以写"它会天天写流水账。要明确：不写进度、不复述对话、没真变化就别写。

### 验证

- 写一条 → 读回来链是 `hashOk: true`
- 立刻再写 → 被最小间隔拦住
- 写 800 字 → 被长度拦住
- 手工改一行历史 → 注入时能看到 `⚠️链断`

### 可以直接发给 AI 的需求

> 给我的机器人做一本"只准追加"的成长笔记：
> 1. 存储用 JSONL，一行一条，只允许 append，不提供任何修改/删除接口
> 2. 每行存上一行的哈希串成链，读的时候校验，被改过要能标出来
> 3. 时间戳带完整日期
> 4. 三条限流：单条字数、每天条数、最小间隔
> 5. 每次唤醒注入最近 6 条，并明确告诉它"不写流水账、没真变化就别写"
> 6. 给我两个工具：写一条、读历史
> 做完把链校验和限流都实测一遍给我看。

## 六、网页控制台：看得见才敢信

### 痛点

链路断了，你说"打不开"，但不知道断在哪一层。日志要翻四五个文件，还都是编码乱的。

### 设计

一个本地单页控制台，把"现在到底怎么样"摊开：模式、在线状态、白名单、队列、最近收发、各组件进程。

三个必须：

1. **本地限定**。只监听 `127.0.0.1`，并且校验 Host 头（只认 `127.0.0.1` / `localhost` / `[::1]`），反代进来一律 403。
2. **令牌鉴权**。首次启动自动生成一个随机 token 存文件，URL 带 `?token=` 或请求头 `x-console-token`，两个都认。
3. **所有 API 都要令牌**。不是只有页面要。这条不做，用 curl 测任何接口都是 401，而且你会以为是接口坏了。

### 坑

1. **curl 总是 401 的真因**：`/api/*` 全部要 `x-console-token` 头。知道这一条能省两小时。
2. **别把管理信息暴露给会话级主体**。AI 调 `/api/status` 时只能用会话 token，它不该看到别人的收发片段和所有权信息。
3. **页面里的 token 要能复用**。刷新页面不该重新要密码——把 token 存进 URL 或 localStorage。

### 验证

- 不带 token 打开 → 401 弹提示
- 带 token 打开 → 能看到状态
- 用 curl 不带 `x-console-token` 打 `/api/status` → 401（这是**预期**行为）
- 带上头 → 200 且状态正常

### 可以直接发给 AI 的需求

> 给我的桥接层做一个本地网页控制台：
> 1. 只监听 127.0.0.1，校验 Host 头，反代返回 403
> 2. 首次启动生成随机 token 存文件，URL `?token=` 和请求头 `x-console-token` 都认
> 3. **所有 `/api/*` 都必须校验令牌**，不只是页面
> 4. 页面上至少能看到：运行模式、连接状态、账号在线、白名单、消息队列、最近收发、各子进程是否活着
> 5. 用会话 token 调用时，隐藏管理级字段
> 做完告诉我不带 token 和带 token 分别会得到什么。

## 最后：六件事之间的关系

```
        语音转文字 ──┐
                     ├→ 让 AI "听得懂、看得见"
        跨会话摘要 ──┘

        传话箱 ──────→ 让 AI "能动手"（跨到本机）
        管理员硬闸 ──→ 让"能动手"这件事只对本人开放
        成长附录 ────→ 让 AI "记得自己变过"
        网页控制台 ──→ 让上面五件事"可以被你看见"
```

这六个能力都不在 DSH 原生插件里。它们更像**一层中间人**：在网关和大脑之间，负责"翻译、转交、校验、记忆、暴露状态"。

**所以，你要不要它们，取决于你想让 bot 像到什么程度。** 只想能聊天，一层都不用加。想让它像个人、能办事、还不闯祸，才值得为此写一层。
